## 1. 入库链路

### 1.1 格式分流 — `DocumentIngestService.read()`

| 扩展名 | Reader | 原因 |
|---|---|---|
| `.pdf` | `PagePdfDocumentReader` | 它带 `page_number`，引用卡的"第 47 页"来自这里；Tika 拿不到页码 |
| `.txt` `.md` | `TextReader` | 显式指定 UTF-8 |
| `.doc .docx .wps .ppt .xls .html` … | `TikaDocumentReader` | 施工现场的规范多以 Word 下发，只认 PDF 会让第一次上传就失败 |

页码字段统一改名：`page_number` → `page`。原文先打 `docId` / `docName`，`TextSplitter` 会把 metadata 复制到每个块。

### 1.2 文本规整 — `normalizeLines()` + `compactNumbers()`

PDF 提取出来的是"版面"不是"句子"，所以切分前必须做两件事：

- **接回被换行切断的句子**（`appendJoined`：中英交界补空格，纯中文直连，避免"高处 作业"）
- **压紧被空格拆开的编号**：`8. 2.1` → `8.2.1`，`2.1. 7` → `2.1.7`，`第 4 章` → `第4章`

> 这一步是"条款切分"能否生效的前提。不规整时，行首锚点几乎匹配不到条款号——改造前 586 个块里有 558 个只能落到"正文片段"。

### 1.3 去水印 — `dropPageFurniture()`

判据三条**同时满足**才丢：短行（≤40 字）+ 全文出现 ≥5 次 + 本身不是条款号。

另有一次"前缀统计"：PDF 常把页脚和下一页首行并成一行，整行不重复、但开头 18 字重复。所以对"句号/分号/空格截断后的前缀"再统计一遍，命中就从行首剥掉。

> 为什么要三个条件：只看"重复"会把反复引用的长条文误删。

### 1.4 按条款断段 — `splitByClause()`

- 行首是**章标题**（`第X章` / `4 临边与洞口作业`）→ 不单独成块，记为 `pendingChapter`，拼到其后第一条前面
- 行首是**条款号** → 断段，新段以条款号开头
- 其余行 → 续行拼接
- 单段 ≤ `chunkSize`（500）→ 整段成块；超长 → `TokenTextSplitter` 兜底再切
- 目录页（`looksLikeToc`：连续 4 个点号 ≥2 处，或 1 处且整段 <120 字）→ 直接丢弃
- 孤立小标题（<30 字且行首无条款号，`mergeMiniHeadings`）→ 并到下一段

> 为什么要"章标题并入"：块里带"属于哪一章"的上下文，召回片段才不至于缺主语。

### 1.5 条款号识别与回溯 — `ClauseLabels` + `DocumentIngestService.split()`

三套正则：

| 写法 | 正则 | 说明 |
|---|---|---|
| `第十二条` | `第[一二三四五六七八九十百零〇\d]+条` | 地方规程 / 企业标准 |
| `3.2.1` | `[1-9]\d?(?:\.\d{1,2}){1,3}` | **至少含一个点**，首位非 0 |
| `附录A` `附录B.2` | `附录\s*[A-Z](?:\.[0-9]{1,2})?` | — |

两个否定判据（这是精华）：

- `proseFollows`：编号后 **20 字符内至少 4 个汉字** → 专治参数表。`1.50 1.8 1.5 1.5` 形状像条款号，但后面没有汉字。
- 数字编号后紧跟 ASCII 字母则跳过（`3.5m` 不是条款号）。

**顺序回溯**：块首认不出条款号时，沿用上一条的条款号，最多传 3 块（`MAX_LABEL_CARRY`）。

> 为什么必须回溯：一条超长条款会被兜底切成 3 块，只有第一块带条款号。若不回溯，后两块在引用卡上又退化成"正文片段"，前面的解析工作全白费。

### 1.6 向量化 — `CachingEmbeddingModel.prefetch()`

默认 `embed(List)` 是**一条文本一次 HTTPS 请求**。171 块的 PDF = 171 次请求，任何一次被中间设备掐断都会让整批入库回滚——这就是"上传 171 块的 PDF 必失败、重建索引要三分半"的真正原因。

做法：入库前按 **5 条一批**批量算好放进 LRU 缓存（批越大响应体越大、越容易断），随后写入时全部命中缓存不发请求。

| 规模 | 改造前请求数 | 改造后 |
|---|---|---|
| 171 块 | 171 | 35 |
| 1221 块 | 1221 | 245 |

### 1.7 异步任务与进度 — `IngestJobService`

- `Executors.newSingleThreadExecutor`：**单线程串行**入库，避免并发写 `registry.json` 与向量库互相覆盖
- `Job` 内 `stage / written / total / message / status` 均为 `volatile`：工作线程写、HTTP 线程读
- 前端轮询 `GET /api/kb/uploads/{jobId}`，`stage` 走"排队中 → 解析切分 → 向量化 → 已完成"

## 2. 检索链路 — `HybridRetriever.retrieve()`

```
问题 ──┬─ 向量路：similaritySearch(topK×3) → 自己重排 → min-score 0.60 过滤
       └─ BM25 路：全库打分 → 原始分 ≥1.5 → 准入判断
                        ↓
                   RRF 融合 → topK
```

### 2.1 第一路：向量检索

- 候选数 `candidateN = topK × 3`
- `similarityThreshold(0.0)` 交给应用层手动过滤——便于统一口径和打日志
- **不信任向量库的返回顺序**：自己按 `getScore()` 重排一遍。RRF 完全依赖名次，名次错了整个融合结果就错
- 低于 `min-score`（0.60）的候选直接丢
- 连接重试：最多 3 次，退避 300ms×n。判定用 `VectorStoreErrors.isConnectionFailure`——Qdrant 走 gRPC，抛的是 `StatusRuntimeException`，沿用旧的 `catch (ResourceAccessException)` 会静默失效；检索是只读操作，重试安全

### 2.2 第二路：BM25

- 自研倒排索引，无第三方依赖。中文分词用 **字符 bigram + 单字**，英文数字按整词
- Okapi BM25：`k1 = 1.5`、`b = 0.75`，IDF 带平滑 `ln(1 + (N - df + 0.5)/(df + 0.5))`
- 候选放宽到 `max(candidateN × 4, 50)`，避免门槛截断把合规块挡掉

### 2.3 两道筛子（重点，各管一件事）

**第一道：`min-score` 管"够不够像"**

实测原始分分布（12 正样本 + 3 负样本）：

```
正样本  0.648 ───────────────────── 0.847
              ↑ 0.07 空白带，0.60 落在中间 ↑
负样本  0.475 ─────────── 0.576
```

原来定的是 0.20——在负样本下方，等于没设。

**第二道：BM25 准入管"该不该由它决定有没有召回"**

```java
boolean vectorHasRecall = !vectorScores.isEmpty();
boolean mayIntroduceNew = vectorFailed || demoMode
        || (vectorHasRecall && cfg.bm25IntroduceNewOrDefault());
```

- 向量有召回 → 允许 BM25 补字面强命中的新块（精确术语、条文编号、数字指标）
- 向量无召回 → BM25 一律不许救场。"今天食堂中午吃什么"也会命中几条食堂条款——那样"无召回不编造"就成了死代码
- 两个例外无条件放开：向量库故障、演示模式（哈希向量无语义判别力，只能靠 BM25 兜底）

> 关键是**BM25 的决定权挂在向量路的结论上**，而不是自己判断。这是这个项目修过的一个真实缺陷。

### 2.4 RRF 融合

```java
combined = 1.0 / (60 + vectorRank) + 0.25 / (60 + bm25Rank)   // 未命中该路记 0
```

为什么不用线性加权（`0.7×向量分 + 0.3×BM25分`）：BM25 归一化后 top1 恒为 1.0，乘 0.3 就是 0.3 分；而向量相邻两名只差 0.02。**量纲不可比**，加权的必然结果是 BM25 霸榜。实测加权把 MRR 从 0.917 拖到 0.767。

`fusion: weighted` 保留了做对照实验。

### 2.5 范围限定 — `docFilter()`

- 向量路：`SearchRequest.filterExpression` → Qdrant 转 payload 的 `must` 条件，**先筛元数据再算距离**。单篇用 `EQ`、多篇用 `IN`（Spring AI 的通用 `Filter.Expression`，换库时这行代码没动）
- BM25 路：倒排索引没有 docId 维度，只能用 `registry.chunksOf(docId)` 拼块 id 集合在应用层过滤

> 为什么必须下推：若"先召回再丢掉"，限定范围很小时 topK 条可能被范围外的块占满，看起来像无召回。

## 3. 生成链路 — `ChatService`

### 3.1 手写 Prompt，不用 Advisor

```
【规范原文】
[1] 《GB50720-2011》3.2.1（第47页）：
    原文 ...
[2] ...
【问题】
{question}
```

SYSTEM_PROMPT 四条硬约束：只依据原文、每个结论标 `[n]`、不足要明说"未覆盖"、不要猜。

> 为什么不用 `QuestionAnswerAdvisor`：它把"检索 → 拼上下文"封装成一键方案，省事但黑盒。答辩时被问"上下文怎么拼、怎么防编造"就讲不清了。

### 3.2 无召回拦截

`prepare()` 返回空 hits → 直接返回固定话术，**不发生任何模型调用**。

### 3.3 流式三层保护 — `streamTokens()`

模型流式调用有个坑：异常在订阅之后才发生，外层 `try/catch` 接不住（这是"对话请求失败 500"的真实原因）。所以：

1. `retryWhen`：仅当 **未输出任何 token** + 连接类异常 + 8 秒内，退避重试一次
2. **换链路**：仍失败则用非流式 `call()` 补答（走 RestClient 连接池，与 WebClient 不是同一批连接），补到就逐块推给前端
3. 都不通 → 抽取式（把召回原文按条拼出来，标注出处）

边界处理：如果**已经吐出部分 token** 才断，不让模型重答一遍（会内容重复），直接补一段"以下为召回到的规范条款原文"。

### 3.4 引用卡片的数据来源

`prepare()` 里组装 `CitationDto`：文档名 / 条款号 / 页码 / 原文片段（截 300 字）/ 相似度。

展示的相似度**必须取 `vectorScore`**，不能取融合分——RRF 分是 `1/(60+rank)` 量级，用户会看到 0.016 这种没法解释的值。BM25 单独引入的块没有向量分，才退回融合分。

### 3.5 SSE 事件序列 — `ChatController.stream()`

```
prepare() 同步执行（改写 + 检索，引用在流开始前就确定）
  ↓
rewrite    （发生改写时才有）→ 前端显示"已结合上下文理解为…"
  ↓
token × N  （逐段正文）
  ↓
citations  （引用列表 JSON，一次性下发）
  ↓
done
```

## 4. 多轮追问 — `QuestionRewriter`

**不是每轮都改写。** 判据：有历史 **且**（问题 <12 字 **或** 命中指代词正则）。

指代词正则：`它|他们|其|这个|那个|这些|那些|上述|前面|刚才|前者|后者|还有|另外|该规范|该条|该项|该要求|怎么样呢|呢$`

其他约束：

| 项 | 值 | 原因 |
|---|---|---|
| 历史条数 | 最近 6 条 | 约 3 轮，再多只会拖慢改写 |
| 单条截断 | 220 字 | 助手回答动辄几百字 |
| 改写结果上限 | 80 字 | 超了说明模型在解释而不是改写，回退原文 |
| 失败策略 | 回退原问题 | 改写是锦上添花，不能因为它挂了就问不了问题 |
| 演示模式 | 不改写 | 没有可用聊天模型，硬改只会改坏 |

`sanitize()` 会去掉"改写后："前缀和多行说明、成对引号——实测模型偶尔会输出这些，直接检索会污染查询。

改写结果**只用于检索**，前端展示始终是用户原话，另有一行提示让用户能发现"理解偏了"。

## 5. 检索评测 — `EvalService`

内置评测集 `eval/default-eval-set.json`：12 条正样本（6 条用规范原词、6 条改口语问法）+ 3 条负样本。

**同一问题并排跑两种模式**：`runOne(case, topK, docIds, hybridOverride)`，传 `FALSE` 得到纯向量，传 `null` 按配置走混合。

| 指标 | 含义 |
|---|---|
| Hit@1 | 正确条款排名第 1 的条数 |
| Hit@K | 前 K 条里命中正确条款的条数 |
| MRR | `Σ(1/rank) ÷ 正样本数` |
| 拒答准确率 | 负样本返回空结果的比例（命中即"误召回"） |

`vectorTopScore()`：用 `topK=1 + threshold=0` **绕过所有阈值**取向量路 top1 原始分。这是唯一能用来定 `min-score` 的数字——调阈值不能再靠猜。

当前成绩（topK=5）：纯向量 Hit@1 11/12、MRR 0.917、拒答 3/3；混合（RRF）同为 11/12、0.917、3/3。

> 混合在本语料上无增益，要如实说：5 篇同主题规范、1436 块，纯向量已接近饱和，天花板在 q05 那条。

## 6. 关键配置项与依据

| 配置 | 当前值 | 依据 |
|---|---|---|
| `app.retrieval.min-score` | 0.60 | 实测正 0.648~0.847 / 负 0.475~0.576，取空白带中点 |
| `app.retrieval.fusion` | `rrf` | 线性加权的量纲问题会把 MRR 从 0.917 拖到 0.767 |
| `app.retrieval.rrf-k` | 60 | 经典取值，名次差距被压平的程度可接受 |
| `app.retrieval.vector-weight` / `bm25-weight` | 1.0 / 0.25 | 向量为主、BM25 补充 |
| `app.retrieval.min-bm25-score` | 1.5 | 太低会让只蹭到零星字词的块参与排序 |
| `app.retrieval.bm25-introduce-new` | `true` | 仅在向量路**已有召回**时生效；无召回一律拒绝 |
| `app.retrieval.margin` | 0（关闭） | 尖峰门限实测纯负收益，见下 |
| `app.chunking.chunk-size` / `overlap` | 500 / 60 | 条款整条优先不切 |

**尖峰门限为什么关着**：思路是"top1 减去候选均值太小 → 整批是背景噪声"。实测设 0.04 后，两条正样本（差值仅 0.031/0.035）被误判为无召回，而三条负样本一条都没挡住——因为闲聊完全不沾边、候选分掉得更快，反而形成"假尖峰"。配置项保留，作为换语料时的开关。

## 7. 已知边界（主动说，别等被问）

1. **口语化问法会漏**：「挖基坑的时候边上怎么防止人掉下去」被理解成"基坑作业安全"，召回上下通道与边坡支护，没有指向"临边防护"。评测集里刻意保留未修，作为能力边界证据。改进方向是查询扩展（把口语问法改写成含规范术语的问句，`QuestionRewriter` 已有基础）。
2. **混合检索在本语料上无增益**：同主题小语料已接近饱和，要体现混合价值需要跨领域更大的库。
3. **不支持表格与图纸**：参数表被 `proseFollows` 主动排除（避免碎块），等于放弃表格类问答。
4. **扫描版 PDF 需要先 OCR**：没有文字层时解析直接失败，会在预检阶段提示。

## 8. 高频提问 → 回答要点

| 问 | 答（先说判据，再说为什么） |
|---|---|
| 怎么防幻觉 | 三道：`min-score` 拦无召回 → Prompt 只允许依据编号原文 → 模型挂了降级抽取式也不编 |
| 为什么不用微调 | 规范会改版，微调要重训且无法溯源；RAG 改的是库，能精确到条款 |
| 为什么 Qdrant | 元数据过滤可下推 + payload 条件删除 + 删除幂等；字面匹配用自研 BM25 补。Chroma 的坑（错误文案判集合、删不存在的 id 段错误）在这里都不存在 |
| 块怎么切的 | 按条款编号切（第X条 / 3.2.1 / 附录A）；超长才交给 Token 兜底；章标题并入下一条 |
| 为什么阈值是 0.6 | 实测正负样本之间有 0.07 宽的空白带，不是拍的 |
| 最难的坑 | hosts 文件删了但 VM 参数还在，JDK 不回退系统 DNS → 全链路解析失败，表现是"抽取式 + 相似度 0.004 + 维度 0"。写了启动守卫 + 5 条测试 |
| 系统能扩展吗 | 换模型只改 `base-url` 与 model 名；切分器与 BM25 都是独立类，可替换 |
